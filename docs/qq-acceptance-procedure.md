# 真实 QQ 接入后的验收顺序

本文件是执行步骤，不是通过记录。固定来源为 Aurabot `e9026a99d9db58974363c416eaa9e555499737fa`；具体时间、结果和缺陷另记 `docs/evidence/`。管理凭据、QQ 号、原始私聊和数据库只留在私有运行目录。

## 先建立一条真正的往返

用户在官方页面完成协议确认、机器人账号扫码和设备验证，确认机器人与主人是不同 QQ 账号。工程师核对 OneBot `get_login_info`、Aurabot `loginOk`、唯一主人配置、空群白名单和适配模块；通过后才开启真实发送。

先请用户只发第一条，看到回复再发第二条，不一次性塞入所有测试：

```text
你好大肥鱼，我来验收这个新系统。用你自己的口气，分两三条短消息打个招呼吧。
```

```text
接着刚才，我们现在在验收什么？你叫什么，是什么样的伙伴？
```

检查：真实主人账号入站 → Aurabot 创建的 QQ 会话 → 真实 DeepSeek 请求 → OneBot 发出 → 主人 QQ 收到。记录气泡数量、顺序和是否出现原始 `|||`；用户评估语气自然度。人格源 hash 和管理端回复都不能替代这里的实际 QQ 表现。

只读观察 `/aurabot/api/state` 时，筛选所需字段再输出，不打印完整返回。它含私有身份与会话信息。正常连接应为 `onebot.state=connected` 且 `onebot.problem` 为空。实际 QQ 会话除安全 preset 的 Neko/Web 工具外，还会动态挂载 `remember`、`recall_memory`、`qq_chat_history`、`qq_send_message`；`qq_send_file`、Shell、宿主文件工具必须缺席。`qq_send_message` 当前目标范围仅主人。

## 图片、表情与 Web 工具

1. 用户以 QQ 图片方式发送无文字标签的合成图（左红圆、右蓝正方形），同时问「这张图里从左到右是什么，分别什么颜色，一共几个形状？」。收到准确答复后追问「右边那个有几条边？」。记录真实图片块及后续对话结果，不以文件名推断代替像素识别。
2. 发「找一张开心的 Nekowhale 动图给我，前面说一句找到啦，后面再说一句送给你。」。核对真实 `sticker_search`、`sticker_send` 调用成功，QQ 实际显示并播放 GIF，文字/图片/文字顺序正确；仅返回 Markdown 或 URL 不通过。
3. 发「做一张写着『验收通过』的文字表情，直接发图给我。」。核对 `meme_render` 与实际 QQ 图片；中文字无方框、裁切或乱码。头像文件模板不属于已开放能力。
4. 发「搜索 DeepSeek 官方 API 文档，找到当前 Search/Fetch 说明；再打开找到的官方页面，用两句中文说清楚页面讲了什么并给出处。」。核对实际 `web_search` 和 `web_fetch` 都成功，回复与获取内容一致。用户已授权官方 Search/Fetch 费用，无需再次申请。

## 自然提炼、纠错和新会话召回

自然提炼来自聊天流水，默认整理时间是北京时间 04:00/16:00，每分钟检查一次。每批至少三条非 bot 消息；`/remember` 是主人直接写入的 `source: panel`，模型 `remember` 是 `source: tool`，二者都不能冒充后台 `source: auto`。

每次验收给合成档案换一个唯一编号，下例 `M-1031-A` 只是占位。以下每段分别发送；工程师必须确认实际进入聊天流水，而不是直接写库制造数据：

```text
下面是可清理的合成记忆验收资料，不是我的真实喜好。这几轮先别调用 remember，稍后让后台整理。档案 M-1031-A 里的测试人物长期喜欢海盐汽水。
```

```text
同一个合成档案 M-1031-A：测试人物固定在周六晚上整理相册。
```

```text
合成档案 M-1031-A 的第三条资料：测试人物的收藏主题是蓝鲸。它们都只用于这次验收。
```

通过原生管理接口 `POST /aurabot/api/memory/extract`、JSON `{ "includeToday": true }` 触发一次真实提炼；不修改数据库。另将一个原生 `memory.consolidateTimes` 设为即将到达的时间，观察真实 tick 完成，之后恢复原时间，用于证明后台调度实际接通。人工提炼与定时提炼分别记录，不能混为一项。

在私有数据中核对合成编号、`source: auto`、事实文字明确属于测试档案以及真实模型结果。若模型提前调用 `remember`，记录工具记忆已生效；用新的合成编号重新测后台提炼，不能把已有记忆去重后的零新增直接判为自动提炼通过。

随后分别发三条纠错资料：

```text
更正合成档案 M-1031-A：测试人物的饮品喜好现在改成青柠苏打，原来的海盐汽水偏好已经过时。先别用 remember，等后台整理。
```

```text
合成档案 M-1031-A 里周六晚上整理相册的约定保持不变。
```

```text
合成档案 M-1031-A 的收藏主题仍然是蓝鲸，只更正刚才的饮品喜好。
```

再次真实提炼，检查旧事实 `invalidAt`/`supersededBy`，或有效更新及 `history`；只剩新事实可供正常召回。随后发送原生命令和问题：

```text
/reset
```

```text
只凭长期记忆，不翻 QQ 聊天记录：合成档案 M-1031-A 现在喜欢什么饮品，固定什么时候做什么？不知道就直说。
```

必须核对 QQ 会话 ID 已变化、`/aurabot/api/memory/recalls` 有相关新事实召回，且该回答未调用 `qq_chat_history`。否则仅从 QQ 历史找回答案不能证明长期记忆。再重启 DSH、重新建立 QQ 连接并重开会话后追问一次，验证磁盘持久化而非进程缓存。验收资料通过后可由用户选择保留或用原生记忆管理界面清理；清理不是本次成功的前置条件，不删除真实聊天或用户记忆。

### 本轮发现的上游流水丢失缺陷

原上游整理器在 `extractLines` 返回失败或「内容太少」后仍推进当天全局 `processed`，历史日还会删除流水；只取最后三段的逻辑也会跳过超过 240 行的旧内容。短聊天或临时 API 故障因此可能永远漏记。

本项目在原 hash 校验脚本增加 `src/features/memory.js` 补丁：同一聊天跨日期合并尚未提炼的消息，以日期/聊天游标记录成功批次；失败或不足保留原游标和流水，其他已成功聊天不重复提炼；失败不标记当日调度完成，下一次真实 tick 可重试。仅真实合法 `[]` 算「成功但没有新事实」，缺失/非法模型结果保留重试；完整处理所有分段；异步提炼期间新来的行不随旧快照删除。关闭记忆或每日整理时的 14 天兜底清理也只删已完全消费的日流水，未处理行继续保留；原生长期记忆遗忘策略没有修改。

这是可重试处理，不保证每条事实只提炼一次。同一聊天有多个分段时，前段成功、后段失败会保留整批游标；重试仍会再提炼已成功的前段，沿用上游事实相似度去重。另一聊天已完整成功的批次则由独立游标跳过。不把单元用例的同文本去重成功推广为任意模型改写都严格无重复。

- 修改后 SHA-256：`cdca6f6956d191426d175254a859142cee5855f60debf4415eea6cc98cddcf52`

回归包含故障注入，以验证失败重试、跨日不足累积、同日混合聊天的独立游标、成功空事实、不合法结果、并发到达、超过 240 行的保留、关闭整理后的过期流水保护及多段部分失败。11 项本地回归通过，无跳过。这是单元测试，不能代替上述真实 DeepSeek 和 QQ 验收。当前统一补丁清单共六个文件：Aurabot 的 `hub.js`、`companion.js`、`llm.js`、`memory.js`、`modules/qq-tools/index.js`，以及 Nekowhale 的 `lib/core/image-input.js`。部署仍须工程师审核、停止 DSH、应用并检查六个文件的全部 hash；不得在运行中覆盖源码。

## 主动聊天与未回复行为

`purpose` 保持关闭，只用原生 `speakup`。临时验收配置与用户日常配置分开记录，测试结束恢复日常频率。所有 QQ 主动发送仍限定已确认主人。

1. 在当前白天醒着窗口，将 `idleMinutes/minIntervalMinutes/maxIntervalMinutes` 暂设为 5；这是上游允许的最短值。`maxPerDay` 临时设为 1，`nudge:false`，避免把定时与追问混在一起。保留真实时钟、随机数和原生调度；不直接写 `nextAt`。
2. 从 `/aurabot/api/state` 只取 `speakUp.nextAt/count/last` 等状态，等待距最后来往至少 5 分钟及 `nextAt` 到达后的真实 tick。模型允许 `[沉默]`；若选择沉默，记录为这一次真实决策，继续另一个真实周期直至验证至少一次真实主动送达，不能把沉默包装成已发消息。`/speakup/fire` 手动按钮不替代这个调度测试。
3. 普通日次数达上限后，启用 `nudge:true`，请用户发送「接下来我会暂时不回你，请用一句自然的问句问我现在在做什么。」；收到真实问句后不要回复、不要重启 DSH。由最后 bot 消息起真实等待超过 15 分钟，窗口截止 40 分钟。需要观察的状态是 `nudgedFor` 是否标记了这条最后消息时间，以及是否发生实际追问。此分支 50% 概率选择调用模型，模型还能决定沉默；没有发出消息并不自动意味着故障。
4. 原生追问不占普通 `maxPerDay`，每一条最后 bot 消息最多尝试一次；如果追问自身又是问句，新的最后消息还可能再次进入追问窗口。不能宣称「每天总计最多 N 条」或「永远只追一次」。日常是否启用 nudge 应根据真实表现和用户偏好决定；若需要总追问上限，要另做明确适配，不能虚构已有上限。
5. 使用 `/silent` 验证暂停后真实定时 tick 不再发送，且普通入站不回复；用 `/active` 恢复。命令回复自身是允许的控制回执，不算静音失败。两命令只作用于当前聊天，必须在主人私聊测试。

`hub.lastOwnerChatAt` / `lastBotToOwner` 是进程内状态，重启后清零；nudge 测试中途重启会使该窗口不可比。应先做完主动窗口，再进行重启验收。记录用户对主动频率、口吻及不回复时体验的实际评价。

## 恢复与观察

分别重启 DSH 和 Snow 网关，确认 OneBot 身份匹配、已有 QQ 登录态恢复、无重复发送旧消息、恢复后的新消息能实际往返，并检查长期记忆。扫码后新增网关登录态再做一致性备份、离机校验与隔离恢复；已有未登录备份不能证明 QQ 登录态恢复。观察实际运行时间、重启次数、模型/网关错误和内存峰值，使用准确时间窗，不能把数分钟检查写成长期稳定。
